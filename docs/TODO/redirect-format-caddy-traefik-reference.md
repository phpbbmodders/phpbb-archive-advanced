# Reference: multi-server redirect generator design (external draft)

An external AI-drafted implementation spec for extending `--redirect-format` to
Caddy and Traefik, kept as research material for `todo-redirect-format-caddy-
traefik.md`. Not reviewed or verified claim-by-claim the way this project's own
docs are — treat every specific technical claim below as unverified until it's
actually checked against real Caddy/Traefik docs and a real instance of each,
the same standard applied to `apache`/`nginx` when those were built.

One concrete bug this document pointed at was independently verified and
fixed: the generic nginx `viewtopic.php` fallback used to check `$arg_p`'s
presence while building its destination from `$arg_t` unchecked, producing a
broken `/topics/.html#p123` for a `p`-without-`t` request. See `docs/CHANGES.md`
("Old-URL redirect fix: nginx `p`-without-`t` malformed destination").

---

# phpbb-archive Multi-Server Redirect Generator

## Purpose

Extend the `phpbb-archive` redirect generator so the static phpBB archive can generate equivalent redirect configuration for multiple web servers and reverse proxies from one common set of archive data.

Supported output formats should be:

```text
apache
nginx
caddy
traefik
```

The existing command-line interface should remain conceptually:

```text
--redirect-format apache
--redirect-format nginx
--redirect-format caddy
--redirect-format traefik
```

The important design requirement is that Apache, nginx, Caddy, and Traefik are **rendering targets**, not independent implementations of redirect behavior.

Do not translate one generated configuration into another.

Instead:

```text
phpBB/archive data
        |
        v
common redirect model
        |
        +----> Apache renderer
        |
        +----> nginx renderer
        |
        +----> Caddy renderer
        |
        +----> Traefik renderer
```

All formats must represent the same redirect semantics.

---

# 1. Existing Redirect Behavior

The generated redirect configuration maps old dynamic phpBB URLs into the archive's static URL structure.

The nginx output documents this explicitly: it is generated by `phpbb-archive --redirect-format nginx`, is intended to be included inside the site's `server {}` block, and IDs that were never archived are deliberately allowed to redirect to nonexistent static destinations, producing the same effective 404 behavior.

For the current example archive, the target layout is:

```text
Topic page 1:
https://phpbbmodders.net/topics/<topic-id>.html

Topic page N:
https://phpbbmodders.net/topics/<topic-id>-p<N>.html

Specific post:
https://phpbbmodders.net/topics/<topic-id>.html#p<post-id>

Specific post on page N:
https://phpbbmodders.net/topics/<topic-id>-p<N>.html#p<post-id>

Forum page 1:
https://phpbbmodders.net/forums/<forum-id>.html

Forum page N:
https://phpbbmodders.net/forums/<forum-id>-p<N>.html

User:
https://phpbbmodders.net/users/<user-id>.html
```

The generator must derive these destinations from the archive configuration rather than hard-code `phpbbmodders.net`.

---

# 2. Legacy phpBB URLs

The redirect system handles at least these phpBB endpoints.

## Topic

```text
/board/viewtopic.php?t=507
```

## Topic with post

```text
/board/viewtopic.php?t=507&p=5756
```

The order of query parameters must not matter:

```text
/board/viewtopic.php?t=507&p=5756
/board/viewtopic.php?p=5756&t=507
```

must behave identically.

Additional unrelated query parameters must not prevent a valid redirect unless there is an explicit reason to reject them.

For example:

```text
/board/viewtopic.php?sid=abc&t=507&p=5756
```

should still resolve from `t` and `p`.

## Forum

```text
/board/viewforum.php?f=125
```

## Paginated forum

```text
/board/viewforum.php?f=125&start=450
```

## User profile

```text
/board/memberlist.php?mode=viewprofile&u=123
```

The redirect logic is concerned with the relevant identifiers, not the original query-string ordering.

---

# 3. Common Redirect Data Model

The redirect generator should first construct a server-independent representation.

Conceptually:

```text
topic_post_pages:
    topic_id
    page_number
    post_ids[]

forum_pages:
    forum_id
    start_offset
    page_number

generic targets:
    topic_id + post_id
    topic_id
    forum_id
    user_id
```

For example:

```text
topic_id: 2051
page_number: 2
post_ids:
    12176
    12179
    12180
    ...
```

followed by:

```text
topic_id: 2051
page_number: 3
post_ids:
    15242
    15244
    ...
```

The existing nginx output demonstrates this mapping directly. Topic 2051 has distinct post-ID sets for pages 2 through 6, and each set redirects to the corresponding static page while retaining the `#p<post-id>` fragment.

Forum pagination follows the same principle using the phpBB `start` offset.

For example:

```text
f=6&start=50  -> forums/6-p2.html
f=6&start=100 -> forums/6-p3.html
f=6&start=150 -> forums/6-p4.html
```

The existing nginx output already contains this mapping.

The renderers should consume this common data rather than rediscover pagination themselves.

---

# 4. Redirect Precedence

Ordering is critical.

A request for a known post on page 4 must not be consumed by the generic topic/post rule and sent to page 1.

The effective precedence for `/board/viewtopic.php` must therefore be:

```text
1. Known paginated topic/post mapping
2. Generic valid topic + post
3. Generic valid topic
4. No redirect
```

The nginx output explicitly documents that page-specific mappings are evaluated before the generic redirect so that the more specific mapping wins.

For `/board/viewforum.php`:

```text
1. Known forum + start pagination mapping
2. Generic valid forum
3. No redirect
```

Again, the generated nginx file explicitly places the paginated forum mappings before the generic rule.

For `/board/memberlist.php`:

```text
1. Valid user/profile request
2. No redirect
```

Each renderer must preserve these semantics using the native routing/priority mechanism of its target server.

Do not rely accidentally on implementation-specific ordering where explicit ordering or priority is available.

---

# 5. Topic/Post Pagination

This is the most important special case.

Consider:

```text
/board/viewtopic.php?t=507&p=5756
```

If post `5756` is known to be on page 2 of archived topic 507, the correct destination is:

```text
https://phpbbmodders.net/topics/507-p2.html#p5756
```

not:

```text
https://phpbbmodders.net/topics/507.html#p5756
```

The nginx generator currently represents that mapping as:

```text
if ($arg_t:$arg_p ~ "^507:(5756|5809|6246|6409|6503|6510)$") {
    return 301 https://phpbbmodders.net/topics/507-p2.html#p$arg_p;
}
```

That generated mapping is visible in the current output.

The other renderers do not need to use the same syntax.

They only need to implement the same mapping.

---

# 6. Generic Topic/Post Redirect

If both a valid numeric topic ID and numeric post ID are supplied, but the post is not part of one of the special page mappings, redirect to:

```text
/topics/<topic-id>.html#p<post-id>
```

For example:

```text
/board/viewtopic.php?t=100&p=200
```

becomes:

```text
/topics/100.html#p200
```

The query parameters must be independently recognized. Their order must not matter.

---

# 7. Generic Topic Redirect

A valid topic request containing `t` but no usable `p` redirects to:

```text
/topics/<topic-id>.html
```

For example:

```text
/board/viewtopic.php?t=100
```

becomes:

```text
/topics/100.html
```

The current nginx output has the generic topic fallback following the generic post handling.

---

# 8. Malformed Topic/Post Requests

The generic topic/post redirect should require **both** a valid numeric `t` and valid numeric `p`.

The current nginx output contains:

```text
if ($arg_p) {
    return 301 https://phpbbmodders.net/topics/$arg_t.html#p$arg_p;
}
```

followed by the `$arg_t` fallback.

This permits a malformed request containing `p` without `t` to potentially construct an invalid destination such as:

```text
/topics/.html#p123
```

The common redirect semantics should instead be:

```text
if numeric(t) AND numeric(p):
    topic/post redirect

else if numeric(t):
    topic redirect

else:
    no redirect
```

All four renderers should follow this behavior.

The same validation principle applies to:

```text
f
start
u
```

IDs and pagination offsets are expected to be numeric.

Do not generate malformed destinations from missing or invalid identifiers.

---

# 9. Forum Pagination

Forum pagination must be treated as a first-class redirect feature.

phpBB commonly represents pagination with a `start` offset.

For example:

```text
/board/viewforum.php?f=125&start=50
```

maps to:

```text
/forums/125-p2.html
```

while:

```text
/board/viewforum.php?f=125&start=450
```

maps to:

```text
/forums/125-p10.html
```

The generated nginx configuration contains these explicit mappings.

The mapping can extend substantially. In this archive, forum 125 continues through:

```text
start=2350 -> page 48
```

The generator must therefore use actual archive pagination information and must not assume a small maximum page count.

After all known paginated mappings, the generic forum fallback is:

```text
/board/viewforum.php?f=<id>
    ->
/forums/<id>.html
```

---

# 10. User Profiles

A request containing a valid user ID should redirect:

```text
/board/memberlist.php?mode=viewprofile&u=123
```

to:

```text
/users/123.html
```

The renderer should preserve whatever restrictions the existing generator intends for `memberlist.php`.

At minimum, `u` must be present and numeric.

If the existing implementation deliberately ignores `mode=viewprofile`, preserve that behavior rather than silently introducing a compatibility change.

---

# 11. HTTP Status

All generated legacy URL redirects should remain permanent redirects:

```text
301 Moved Permanently
```

Do not change these to:

```text
302
307
308
```

unless the project explicitly makes that a configurable option in the future.

The current nginx output consistently uses `return 301`.

---

# 12. Old Query String Removal

The destination is the canonical static archive URL.

The legacy phpBB query string should therefore not be carried into the destination.

For example:

```text
/board/viewtopic.php?t=507&p=5756&sid=abcdef
```

must redirect to:

```text
/topics/507-p2.html#p5756
```

not:

```text
/topics/507-p2.html?t=507&p=5756&sid=abcdef#p5756
```

Likewise:

```text
/board/viewforum.php?f=125&start=450
```

becomes:

```text
/forums/125-p10.html
```

without the original `f` or `start` query parameters.

Each renderer must explicitly guarantee this according to the behavior of its target server.

---

# 13. Apache Renderer

Apache should continue to use `mod_rewrite`.

The Apache implementation has an important limitation that should remain documented:

`RewriteCond` `%N` backreferences refer to captures from the relevant condition expression and must not be treated as a general accumulator of captures across arbitrary separate conditions.

The renderer therefore needs to ensure that values needed in the replacement are captured reliably.

For legacy query strings, it may need to account for:

```text
t before p
```

and:

```text
p before t
```

when matching the raw query string.

This is an Apache-specific implementation concern.

It must **not** leak into the common redirect model.

Expected conceptual output:

```text
RewriteEngine On

# specific paginated topic/post mappings
...

# generic topic + post
...

# generic topic
...

# paginated forums
...

# generic forum
...

# user
...
```

The Apache renderer should retain the existing proven behavior unless a change is required to bring it into the shared semantic test suite.

---

# 14. nginx Renderer

nginx provides parsed query arguments through variables such as:

```text
$arg_t
$arg_p
$arg_f
$arg_start
$arg_u
```

This is preferable to matching the raw query string.

The current renderer already takes this approach.

Example:

```text
location = /board/viewtopic.php {
    ...
}
```

and page-specific mappings compare:

```text
$arg_t:$arg_p
```

against known topic/post combinations.

This makes query parameter order irrelevant.

The nginx renderer should continue using parsed arguments.

The generic topic/post condition should, however, require both numeric `t` and numeric `p`, rather than checking only whether `$arg_p` exists.

The generated file should remain suitable for inclusion inside:

```text
server {
    include ...;
}
```

as documented by the generated header.

---

# 15. Caddy Renderer

Caddy should be implemented using native Caddyfile request matching and redirect facilities rather than by mechanically translating Apache regular expressions.

Official Caddy documentation confirms that request matchers can match:

```text
path
path_regexp
query
expression
```

and other request properties.

The `query` matcher works with parsed query parameters. Different query keys in the same matcher are ANDed, while values for the same key can be ORed. This is particularly useful because it avoids depending on query-string order. ([Caddy Web Server][1])

Official documentation:

[Caddy Request Matchers](https://caddyserver.com/docs/caddyfile/matchers?utm_source=chatgpt.com)

Caddy's `redir` directive performs client redirects and supports `permanent`, which corresponds to HTTP 301. ([Caddy Web Server][2])

[Caddy redir directive](https://caddyserver.com/docs/caddyfile/directives/redir?utm_source=chatgpt.com)

For mutually exclusive routing, Caddy's `handle` blocks evaluate only the first matching sibling handle; an unmatched `handle` can act as a fallback. ([Caddy Web Server][3])

[Caddy handle directive](https://caddyserver.com/docs/caddyfile/directives/handle?utm_source=chatgpt.com)

The Caddy renderer should therefore use Caddy-native semantics for:

```text
exact legacy path
+
query parameter matching
+
specific-before-generic routing
+
301 redirect
```

Do not assume that Apache `%N` captures or nginx `$arg_*` variables have direct Caddy equivalents.

Generate valid Caddy syntax from the common redirect model.

Where dynamic values are required, use documented Caddy placeholders and/or regular-expression captures.

Caddy placeholders are designed to inject request-derived values into directive arguments. ([Caddy Web Server][4])

[Caddyfile Concepts and Placeholders](https://caddyserver.com/docs/caddyfile/concepts?utm_source=chatgpt.com)

Because this file is generated rather than hand-maintained, correctness and predictable precedence matter more than minimizing the number of generated lines.

---

# 16. Caddy Ordering

Do not assume textual order alone will always provide the intended result.

Caddy has its own directive sorting rules. Its documentation explicitly notes that directive evaluation order matters and that `route` can be used when literal ordering is required. ([Caddy Web Server][5])

[Caddyfile directive order](https://caddyserver.com/docs/caddyfile/directives?utm_source=chatgpt.com)

The generated Caddy configuration must guarantee:

```text
specific paginated mapping
    before
generic mapping
```

Use `handle`, nested `handle`, `route`, or another documented mechanism as appropriate.

The implementation should be validated with Caddy's configuration parser rather than relying only on visual inspection.

---

# 17. Traefik Renderer

Traefik is architecturally different from Apache, nginx, and Caddy.

Its HTTP routers decide whether a request matches.

A router can then invoke middleware.

The RedirectRegex middleware performs the actual redirect.

Therefore the conceptual model is:

```text
request
   |
   v
router rule
   |
   v
redirect middleware
```

not:

```text
single rewrite directive
```

Traefik router rules support request matching including:

```text
Path
PathRegexp
Query
QueryRegexp
```

and router priority can be explicitly configured. ([Traefik Docs][6])

Official documentation:

[Traefik HTTP Router Rules and Priority](https://doc.traefik.io/traefik/routing/routers/?utm_source=chatgpt.com)

RedirectRegex matches the request URL and constructs a replacement using regular-expression captures. The middleware also supports permanent redirects. ([Traefik Docs][7])

[Traefik RedirectRegex middleware](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/redirectregex/?utm_source=chatgpt.com)

---

# 18. Traefik Priority

Explicit priority is important.

Traefik normally derives router priority from rule length. The documentation states that routes are sorted by rule length unless an explicit priority is supplied. ([Traefik Docs][6])

Generated archive redirects should not depend on incidental differences in generated rule length.

Assign explicit priorities so that:

```text
specific topic/post page mapping
>
generic topic/post
>
generic topic
```

and:

```text
specific forum/start mapping
>
generic forum
```

The exact numeric priority scheme is an implementation choice, but it must be deterministic and tested.

For example, conceptually:

```text
300 = specific paginated redirects
200 = generic ID + secondary-ID redirects
100 = generic single-ID redirects
```

The actual values are less important than the guaranteed relationship.

---

# 19. Traefik RedirectRegex Escaping

The renderer must account for Traefik configuration syntax.

The official RedirectRegex documentation notes several important details:

1. The regex matches the request URL.
2. Replacement captures should use `${1}` style rather than ambiguous forms such as `$1x`.
3. YAML escaping may require backslashes to be doubled.
4. Docker labels require dollar signs to be doubled. ([Traefik Docs][7])

This raises an output-format question for the project.

`traefik` should have one clearly defined generated representation.

Recommended default:

```text
Traefik dynamic configuration in YAML
```

rather than Docker labels.

Generating labels for hundreds of archive redirect mappings would be cumbersome and provider-specific.

If label output is desired later, treat it as a separate format or sub-format rather than mixing label escaping into the normal Traefik renderer.

For example:

```text
--redirect-format traefik
```

could mean dynamic YAML.

A future extension could provide something such as:

```text
--redirect-format traefik-labels
```

only if there is an actual use case.

---

# 20. Do Not Build an Apache-to-X Converter

Do not implement:

```text
Apache rules
    -> parser
    -> nginx
```

or:

```text
Apache rules
    -> parser
    -> Caddy
```

or:

```text
Apache rules
    -> parser
    -> Traefik
```

That would make Apache syntax an accidental internal API and preserve Apache-specific limitations in every renderer.

Instead:

```text
archive database/data
        |
        v
redirect model
        |
        +--> apache
        +--> nginx
        +--> caddy
        +--> traefik
```

The existing nginx implementation already demonstrates why this is preferable: nginx can work directly with parsed `$arg_*` variables instead of reproducing Apache's raw-query matching strategy.

---

# 22. Pagination Boundary Tests

Tests should include the first and last post of each generated topic page mapping.

For example, if topic 2051 page 2 contains:

```text
12176 ... 15241
```

test both boundaries.

Then test page 3 boundaries.

This catches accidental overlap or omissions between generated post groups.

The same should be done for forum pagination.

For forum 125, test several mappings including a high page number because the current archive contains mappings extending to page 48.

This ensures the implementation does not accidentally impose a small-page assumption.

---

# 23. Query-Order Tests

Every renderer must be tested with parameter order reversed.

At minimum:

```text
?t=507&p=5756
?p=5756&t=507
```

and:

```text
?f=125&start=450
?start=450&f=125
```

Also test unrelated parameters before, between, and after relevant parameters:

```text
?sid=x&t=507&p=5756
?t=507&sid=x&p=5756
?t=507&p=5756&sid=x
```

They should resolve identically.

This is especially important for Apache because Apache's renderer may inspect the raw query string, whereas nginx, Caddy, and Traefik have higher-level query matching facilities.

---

# 24. Generated Configuration Validation

Tests should go beyond string comparisons where practical.

## Apache

Validate syntax using an Apache configuration test in CI if Apache is available.

Typical deployment validation:

```text
apachectl configtest
```

## nginx

Validate generated configuration with:

```text
nginx -t
```

inside a minimal test server configuration that includes the generated file.

## Caddy

Validate/adapt the generated Caddyfile with Caddy's own tooling.

The test should ensure the generated configuration parses successfully before behavioral testing.

## Traefik

Load the generated dynamic configuration into an appropriate Traefik test configuration and ensure Traefik accepts it.

Syntax-valid output is necessary but not sufficient.

Behavioral tests should then issue HTTP requests and inspect the resulting:

```text
Location
```

and status code.

---

# 25. Behavioral Integration Tests

Where server binaries are available in CI, launch each target server locally and run the same request matrix against it.

The test should verify:

```text
status == 301
```

and:

```text
Location == expected canonical archive URL
```

This gives the project an unusually strong guarantee:

```text
Apache behavior
==
nginx behavior
==
Caddy behavior
==
Traefik behavior
```

even though their generated configuration syntax is completely different.

---

# 26. Deterministic Output

Generated redirect files should be deterministic.

Given the same archive data and configuration, two runs should produce byte-for-byte equivalent output.

Sort mappings consistently by:

```text
topic ID
page number
post ID
```

and:

```text
forum ID
page number/start offset
```

Do not depend on database row ordering unless it is explicitly guaranteed.

Deterministic output makes:

```text
git diff
```

useful and prevents meaningless changes in generated redirect files.

---

# 27. Comments in Generated Files

Each generated format should contain a short header explaining:

```text
what generated the file
which --redirect-format produced it
where it should be included
that it should be regenerated rather than manually maintained
what happens to IDs absent from the archive
```

The existing nginx header is a good model.

Page-specific sections should also explain why they occur before generic fallbacks.

Do not generate excessive comments for every individual rule.

Use comments at structural boundaries.

---

# 28. Suggested File Structure

Exact project structure should follow the existing repository, but conceptually separate data generation from rendering.

For example:

```text
redirects/
    model.py
    apache.py
    nginx.py
    caddy.py
    traefik.py
```

or equivalent modules within the existing project architecture.

The model should expose server-neutral records.

For example:

```text
TopicPostPageRedirect
ForumPageRedirect
```

plus the archive base URL and legacy board path.

Do not make individual renderers query the database independently unless that is already an unavoidable architectural requirement.

---

# 29. Preserve Existing CLI Compatibility

Do not break existing users of:

```text
--redirect-format apache
```

or:

```text
--redirect-format nginx
```

unless a demonstrated bug requires a correction.

Adding:

```text
caddy
traefik
```

should extend the existing accepted choices.

Invalid values should continue producing the project's normal CLI validation/error behavior.

Do not introduce unrelated CLI changes as part of this work.

---

# 30. Preserve Configurability

Do not hard-code:

```text
https://phpbbmodders.net
```

or:

```text
/board/
```

unless those values are already intentionally hard-coded by the project's configuration model.

The redirect generator should use the same archive URL and source-board path information used by the existing Apache/nginx generators.

The uploaded file is an example output, not a specification that every archive lives at that hostname.

---

# 31. Security and Escaping

Values originating from configuration must be escaped appropriately for the output format.

This particularly applies to:

```text
hostnames
paths
regex literals
YAML strings
Caddyfile tokens
Apache regex/replacement strings
nginx strings
```

Numeric database IDs should be treated as integers before rendering rather than blindly interpolating arbitrary database strings.

Do not solve escaping by applying one generic escape function to all four formats.

Each renderer owns its target-specific escaping.

# 34. Implementation Sequence

Recommended development sequence:

```text
1. Identify/refactor existing redirect data generation.

2. Establish the common redirect model.

3. Move or adapt Apache rendering onto that model.

4. Move or adapt nginx rendering onto that model.

5. Verify existing Apache/nginx output behavior.

6. Add shared semantic tests.

7. Correct the malformed nginx p-without-t case.

8. Implement Caddy renderer.

9. Validate Caddy syntax.

10. Run shared behavioral cases against Caddy.

11. Implement Traefik dynamic-YAML renderer.

12. Add explicit Traefik priorities.

13. Validate Traefik configuration.

14. Run shared behavioral cases against Traefik.

15. Add documentation/examples.

16. Run complete regression suite.
```

Do not begin by writing hundreds of Caddy or Traefik rules directly into the existing Apache/nginx generator.

Establish the shared semantics first.

# 35. Acceptance Criteria

The work is complete when all of the following are true.

```text
[ ] --redirect-format apache works.

[ ] --redirect-format nginx works.

[ ] --redirect-format caddy works.

[ ] --redirect-format traefik works.

[ ] Existing Apache behavior is preserved except for explicitly
    documented correctness fixes.

[ ] Existing nginx behavior is preserved except for explicitly
    documented correctness fixes.

[ ] Known posts on topic pages >1 redirect to the correct -pN page.

[ ] Post fragments (#p<ID>) are preserved.

[ ] Generic topic/post redirects work.

[ ] Generic topic redirects work.

[ ] Forum pagination redirects to the correct -pN page.

[ ] Generic forum redirects work.

[ ] User redirects work.

[ ] Query parameter order does not affect behavior.

[ ] Unrelated extra query parameters do not break valid redirects.

[ ] Old phpBB query strings are not retained in canonical destinations.

[ ] p without t does not construct /topics/.html.

[ ] Invalid/non-numeric identifiers do not construct malformed URLs.

[ ] All redirects use HTTP 301.

[ ] Specific pagination mappings always outrank generic mappings.

[ ] Caddy output passes Caddy configuration validation.

[ ] Traefik output passes Traefik configuration validation.

[ ] nginx output passes nginx configuration validation.

[ ] Apache output passes Apache configuration validation where tested.

[ ] Shared behavioral tests produce equivalent results across all
    supported servers.

[ ] Generated output is deterministic.

[ ] Archive hostname/path values come from existing configuration,
    not hard-coded example values.

[ ] Existing CLI compatibility is preserved.
```

# 36. Scope Discipline

Do not use this work as an excuse for unrelated refactoring.

Changes should be limited to:

```text
redirect data/model
redirect renderers
CLI format choices
redirect tests
redirect documentation
```

Preserve existing public interfaces and configuration unless changing them is required for the new formats.

If an existing behavior looks questionable but is unrelated to cross-server redirect generation, document it separately rather than silently changing it.

The one exception worth addressing as part of this work is the generic nginx `p`-without-`t` case because it directly affects semantic equivalence among the renderers.

---

# 37. Core Design Rule

The final implementation should have exactly one definition of **what a redirect means** and multiple definitions of **how that redirect is expressed**.

In short:

```text
One redirect model.
One behavioral test matrix.
Four renderers.

Apache != canonical representation.
nginx  != canonical representation.
Caddy  != canonical representation.
Traefik != canonical representation.

Archive redirect semantics are canonical.
```

That architecture will make additional targets possible later without having to reverse-engineer another server's generated configuration.
