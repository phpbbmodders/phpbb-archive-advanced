# Structural changes and features since the original

Everything below was added on top of matildepark's original 4 commits (`b079b39`..`8b627fa`) while archiving a real, large phpBB 3.3.x board (phpbbmodders.net — 4300+ topics, 26800+ posts, 8100+ users).

## New CLI flags

| Flag | Does |
|------|------|
| `-m`/`--missing-avatars` | Diagnostic mode: lists users whose avatar can't be fetched/decoded, writes a starter `--avatar-overrides` template |
| `--avatar-overrides FILE` | JSON mapping `user_id` → local image, for avatars the generator can't resolve on its own |
| `-l`/`--list-forums` | Diagnostic mode: prints every forum/category with its `forum_id`, indented to show nesting |
| `--exclude FILE` | JSON `{"categories": [...], "forums": [...]}` — recursively excludes forums/categories, and any attachment or external image used only inside them, from the archive entirely |
| `-i`/`--check-images` | Diagnostic mode: lists external `[img]`/`<IMG>` URLs that fail to resolve, writes `output/unresolved_images.json` |
| `--url-mirrors FILE` | JSON `{"url_prefix": "local_dir"}` — resolves external images from a local directory instead of the network, for hosts that block the generator |
| `--incremental` | Keeps previously-downloaded attachments/avatars/external images across runs; only failed URLs retry. Generated HTML pages are still rebuilt fresh every run |
| `--ignore-hosts FILE` | JSON array of hostnames to skip entirely without a network attempt — for hosts already confirmed permanently dead |
| `--attachment-recovery DIR` | A separately-collected backup (same layout as an attachment source) checked for a working copy of any attachment missing/corrupted in the main dump |
| `--style-css FILE` | Replaces the built-in neutral stylesheet with a custom one — see below |
| `--announcement FILE` | Shows a notice on index/forum/topic pages — see below |
| `--sitemap-url URL` | Writes `sitemap.xml`/`robots.txt` for that absolute base URL — see below |
| `--search` | Adds `search.html`, indexed with Pagefind — see below |
| `-c`/`--check-links` | Diagnostic mode: scans an already-generated `output/` for internal links that don't resolve, writes `output/broken_links.json` — see below |
| `--profile-position {left,right}` | Which side of a post the poster's profile sidebar sits on in viewtopic. Defaults to left, matching phpBB's own layout |
| `--favicon FILE` / `--favicon-url URL` | Favicon from a local file or fetched live — see below |
| `--logo FILE` / `--logo-url URL` | Board logo shown in the header, from a local file or fetched live — see below |
| `--logo-natural-size` | Shows the logo at its own original size instead of scaling it to fit the header |
| `--theme {light,dark}` | Which built-in neutral palette to use. No effect when `--style-css` is given |
| `--board-hosts FILE` | Extra hostnames this board is also known to have used, for internal-link rewriting — see below |
| `--redirect-format {apache,nginx}` | Writes a server-config snippet 301-redirecting the live board's old dynamic URLs to this archive's own pages — see below |
| `--redirect-old-prefix PATH` | Overrides the auto-detected old install path used by `--redirect-format`'s rules — see below |

## Corrupted and missing content

- **Attachment recovery**: `find_bad_attachments()`/`_attachment_is_valid()` validate every image, zip, and rar attachment (Pillow for images, `zipfile.testzip()` for zip, the system `7z` binary if present for rar); anything missing or invalid is dropped from rendered posts rather than left as a broken link. `--attachment-recovery` checks a secondary backup directory for a working copy before giving up on one. Generalizing past images mattered in practice: 205 of 209 `.zip` and 24 of 24 `.rar` attachments in a real dump failed validation ("valid archive data followed by trailing garbage"), and 92% of each had a genuinely working copy sitting in the recovery backup the whole time, previously never checked because only images were.
- **phpBB's own thumbnail files copied into the archive as unreferenced junk**: `copy_assets()` walked and copied every file under `dump/files/` with no concept of what actually belongs there — including phpBB's own auto-generated `thumb_<attach_id>_<physical_filename>` companion files for image attachments, a separate concept never referenced by its own name in `phpbb_attachments` (this archive always serves the full image directly; it doesn't generate or link to thumbnails). Confirmed real: 1,498 such files sitting in a stray nested `dump/files/files/` subdirectory (from an old, since-identified faulty backup script), the majority of them *also* corrupted/truncated independent of being pointless — dead weight with no purpose in the generated output. Now skipped at copy time (anything not a real attachment's own `physical_filename` is ignored entirely), with the same `--incremental` blind-spot cleanup already applied to newly-excluded attachments extended to cover this: a prior run's already-copied junk gets removed too, not just newly skipped. Confirmed on a real regeneration: 751 stale files removed, 0 remaining.
- **Attachment recovery across the dump's own duplicate copies**: the same physical_filename can have more than one on-disk copy when a dump has stray nested duplicate subdirectories (see above) — `copy_assets()` used to flatten by simply keeping whichever copy `os.walk()` found first (the shallowest), without checking whether it actually validates. Attachment copying now collects every copy of a given file across all nesting levels first, and falls back to a deeper copy that validates if the shallowest one doesn't (see `_attachment_is_valid`) — the same recovery `--attachment-recovery`'s external backup directory already does, applied to the dump's own internal duplicates too. On phpbbmodders.net's own dump this had no measurable effect in practice: the nested copies turned out to be byte-for-byte duplicates of the same corrupted source (the faulty backup script cloned files as-is, corruption included, rather than collecting them independently at different times), so there was nothing to recover from — but the logic is real, unit-tested, and matters for a dump whose duplicate copies do come from genuinely independent collection events.
- **Real attachment filenames**: `assets/attachments/<physical>` was flattened to a single file per physical_filename, so a browser's "Save Image/Link As" produced the meaningless on-disk hash rather than the attachment's actual name — the existing `download="<real_filename>"` attribute on non-image attachment links only covered a plain-click save, not a right-click "Save As" on the underlying URL. Each attachment now lives in its own `physical_filename` subdirectory containing one file named after its `real_filename` (`assets/attachments/1706_79dc.../mchat_deathwing.gif`), so the served URL itself ends in the real name. An inline image is now also wrapped in an `<a href download>` linking to that same path, so right-click "Save Image As" works too, not just a plain click-through.
- **Missing/corrupted smilies**: `find_bad_smilies()` mirrors the image-decode half of the attachment/avatar checks for phpBB's own smiley pack — a missing or undecodable smiley file falls back to its raw code text (`:)`) rather than a broken `<img>`, the same treatment already given an unrecognized smiley code.
- **Avatar recovery**: same validation applied to avatars (local uploads and remote). `download_remote_avatars()` fetches and caches remote avatars locally (with browser User-Agent + Referer spoofing — some hosts block the generator's plain requests as hotlinking); `--avatar-overrides` covers the ones that still can't be resolved (dead host, bot protection).
- **External images**: `[img]`/`<IMG>` URLs in posts, signatures, and forum descriptions are downloaded and cached locally (`download_external_images()`) so the archive stays self-contained, rather than linking out to URLs that will eventually rot.
- **`postimg.org` → `postimg.cc` recovery**: `postimg.org` itself is a parked/dead domain (confirmed by fetching it directly — it now shows a for-sale page), but old `postimg.org` links still resolve once rewritten to `postimg.cc`, the same service's current domain, keeping the same subdomain and path (`http://s25.postimg.org/…` → `http://s25.postimg.cc/…`, verified against real links from this dump). `_fetch_image()` retries once against the rewritten host before giving up, and whatever resolves is cached locally exactly like any other external image — no separate mechanism.
- **Missing post/topic content**: if a topic's post rows are missing from the dump entirely, or just its opening post, `topic.html` says so explicitly instead of silently rendering an empty or truncated thread.
- **Attachment path flattening**: some dumps end up with attachments duplicated in stray nested subdirectories from how they were originally collected; `copy_assets()` flattens by basename, keeping the shallowest copy on a name collision.
- **Malformed `[img]` tags from a botched phpBB2→3.x migration**: a board that started on phpBB2 can end up with literal `[img]`/`[/img]` bracket text left in the stored XML markup around content a *different* auto-conversion pass already touched, instead of a proper `<IMG>` element — three shapes found on a real board (665/4/277 posts): `[img]<URL url="X">...</URL>[/img]` (sometimes with stray characters on either side — a trailing `.`, or a mangled `ttp://` fragment where the migration also dropped the leading `h`), `[img]<ATTACHMENT ...>...</ATTACHMENT>[/img]`, and a bare `[img]url[/img]` never converted at all, typically nested inside an already-correctly-converted `<URL>` link (phpBB's "clickable thumbnail" pattern). All three resolve the same way the existing `<IMG>` handling does; the bare-URL case is scoped to content that's *exactly* a URL, so it can't match posts that merely discuss `[img]` as text (verified against real posts quoting phpBB's own BBCode config array, and one describing an unrelated bug inside a `[code]` block).
- **Lazy-loaded images**: every post/attachment/avatar `<img>` is marked `loading="lazy"`, so a long thread with dozens of embedded images doesn't force the browser to fetch all of them up front.
- **XML-format smilies (`<E>code</E>`)**: phpBB 3.2+'s XML post storage represents a smiley as `<E>:code:</E>` rather than the older `<!-- s... --><img .../><!-- s... -->` HTML-comment form `_convert_smilies()` already handled. Without a specific handler, the generic "strip unknown XML tags" fallback removed the `<E>` tags but kept the raw code as visible text (`:ugeek:`, `:P`, etc., never converted to the actual smiley image). `_convert_xml_markup()` now resolves `<E>` content against the same `phpbb_smilies` code → filename map; an unrecognized code is left as its raw text rather than dropped.
- **Smiley sizing**: neither smiley path set a `width`/`height` attribute, so a pack whose source image files are larger than their intended display size (a real board's `icon_e_ugeek.png`: 202×214px on disk, `phpbb_smilies.smiley_width`/`smiley_height` says 17×18) rendered huge instead of icon-sized. Both paths now read the dump's own display-size columns — real per-smiley metadata, not a guessed constant — and set the attributes when present; a code with 0×0 (unset in some dumps) falls back to the old unscaled behavior.
- **Attachment-type icons**: a non-image attachment was a bare filename link with no visual cue about what it was. Now shown with a matching Bootstrap Icon (https://icons.getbootstrap.com/, MIT-licensed), inline SVG so the archive stays self-contained (no CDN, matching how every other asset is downloaded and embedded locally rather than hotlinked) — no per-filetype icon set exists in a bare SQL dump to draw a real icon from, so this maps the file's own extension to a real, unmodified Bootstrap Icon rather than a fabricated one. Icon-only, no separate text badge (an earlier version of this feature used a small colored "ZIP"-style text badge instead, dropped as redundant — the extension is already visible in the attachment's own filename right next to it); the extension is still present as the icon's `<title>` for a hover tooltip and screen readers. Real distribution confirmed on phpbbmodders.net's own dump: zip/rar dominate (176/21 real attachments), with pdf/txt/js/wmv/xml/swf/psd in small numbers — the icon mapping covers each of those plus related common extensions (7z/tar/gz, csv/log/rtf/md, php/py/html/css/json/sql/etc., mp4/mp3/etc., ai/eps/svg) for real-world coverage beyond just this one dump, falling back to a generic file icon for anything else.
- **Internal cross-topic links**: a post linking to another topic on the *same* board (`[url=http://.../viewtopic.php?f=16&t=11434]...[/url]`, or the XML `<URL url="...">` equivalent) pointed at the original site rather than the corresponding page in this archive. Both the XML and old-BBCode link paths now check the linked `t=` topic id against the set of topic ids actually in this archive and rewrite it to a relative `topics/N.html` link (preserving a `#pNNNN` post anchor) when it matches; a link to a topic that's excluded, or on an entirely different board, falls through to session-id stripping (below) rather than becoming a broken one. The topic-id check alone wasn't enough — see "Cross-board link redirects" under Security and privacy hardening.
- **Session-id stripping**: any link that isn't rewritten to an internal `topics/N.html` link (an external link, or a `viewtopic.php` link to an excluded/different-board topic) previously passed through with its `sid=<32-hex>` query param intact — meaningless once archived, since phpBB session ids expire almost immediately. `_strip_sid()` removes it from any URL's query string using phpBB's own session-id convention, so it covers any phpBB install, not just this board or phpBB.com.
- **`<LINK_TEXT>` tag leak**: phpBB's `<LINK_TEXT text="shortened display text">full raw URL</LINK_TEXT>` (used when phpBB truncates a long auto-linked URL for display) fell through the generic "strip unknown XML tags" cleanup untouched — that regex requires an all-caps/digit tag name, and `LINK_TEXT`'s underscore falls outside it — so the full raw URL leaked into the rendered post as visible text. Replaced with a dedicated substitution that keeps just the `text` attribute.
- **Linked last-poster names**: the "last post by X" name shown on the index (per forum) and on a forum page (per topic) was plain text, unlike the topic-starter name next to it, which was already a link. Both now link to `users/<id>.html` using the dump's own `forum_last_poster_id`/`topic_last_poster_id` columns, falling back to plain text only when that id is 0 (no poster recorded) **or 1** (phpBB's reserved "Anonymous" account — a real user_id, but not a real profile page).
- **"Started by" showing Unknown for every topic**: the forum-listing template checked `topic.topic_poster_name`, a field that doesn't exist on that row — the real column is `topic_first_poster_name` — so the condition was always false and every single topic's "Started by" silently fell through to "Unknown" regardless of who actually started it. Also guards the topic-starter link against the reserved Anonymous user (id=1), same as the last-poster fix above.
- **Post permalinks**: every post already carried an `id="pN"` anchor (used by the internal cross-topic link rewrite above), but there was no visible way to get a link to one specific post — a viewer would have to know to hand-craft the `#pN` fragment. The post's own "Posted: ..." timestamp is now a link to its own anchor, so right-click → copy link (or just clicking through) gives the exact permalink.

## Security and privacy hardening

Found by an external security review of this generator and verified
against a real, large phpBB dump before fixing (numbers below are all
real, not estimates).

- **Full database left in the publishable output**: `output/.phpbb_archive.db` was created directly under `output/` and only ever closed, never removed — a static-file deployment would publish it alongside the HTML. It's the entire imported dump verbatim: private messages, password hashes, email addresses, and excluded/hidden content included (confirmed: 75MB, 2,451 private messages, both password and email columns intact). The database now always builds in a system-temp file instead, deleted once the run that needed it (`generate()`, or any diagnostic mode) finishes, with a one-time migration cleanup for a stale copy left by an `output/` built before this fix.
- **Private-message attachments leaking into public topic pages**: `post_msg_id` is shared between real posts and private messages (a msg_id for a PM instead of a post_id — separate id sequences that can numerically collide), and `get_attachments(post_id)` matched on `post_msg_id` alone with no way to tell the two apart. Confirmed: 4 of 10 real PM attachments collided with a real post_id, and 3 of those were actually rendered on the corresponding topic page. Fixed with `in_message = 0` on the query. Separately, `copy_assets()` copied every attachment file it found with no concept of "belongs to a private message" at all — all 10 PM attachment files ended up in `assets/attachments/` regardless of collisions; private-message attachments are now excluded from copying unconditionally, the same treatment an excluded forum's attachments already got.
- **`--attachment-recovery`/`--incremental` undoing exclusions**: `find_bad_attachments()` checked every attachment in the database against disk with no idea some were deliberately never copied (excluded forum, or a private-message attachment per above) — it just saw a missing file and reported it as corrupted, so `--attachment-recovery` would restore a "missing" attachment straight from its recovery backup, undoing the exclusion entirely. It now skips anything in the same excluded set `copy_assets()` already respects. Separately, `--incremental` only ever adds attachment files across runs and never revisits ones already on disk, so a newly-added exclusion left over from an earlier run stayed put — confirmed: 114 of 157 excluded-forum attachments were still sitting in `assets/attachments/`. `copy_assets()` now actively removes anything excluded that a prior run already copied.
- **SQL import corrupting real post content**: `import_mysql_dump()` applied its MySQL-syntax cleanup (comment removal, type-keyword stripping, backtick→doublequote, a trailing-comma fixup) as plain regexes over the *entire* file, with no way to tell actual SQL syntax apart from a stored value that merely looks similar. Reproduced on this modding-forum dump, full of real SQL/PHP examples: `unsigned mediumtext /*sample*/ \`tick\`` became ` TEXT  "tick"`, and `call myFunc(a, b,)  and enjoy` lost its trailing comma. A real post literally showing `` ALTER TABLE ... ADD 'x' tinyint(1) UNSIGNED ... `` would have had `UNSIGNED` silently deleted the same way — confirmed against a real one in this dump. `_split_by_string_literals()`/`_apply_outside_strings()` track single-quoted string boundaries so those substitutions only ever run on actual SQL syntax, never on row data. Also rewrote the escape-sequence resolution (`\n`, `\'`, `\\`, etc.) as one coherent left-to-right pass instead of six independent global `.replace()` calls — the old approach could misparse a value ending in an escaped backslash immediately followed by its real closing quote, since a later `.replace()` has no memory of what an earlier one already consumed.
- **Destructive `rmtree` ordering**: a non-incremental run wiped `--output` unconditionally before ever checking `--dump` actually had anything in it, or that `--output` and `--dump` weren't the same directory (or one containing the other) — a mistake there deleted whichever directory the wipe reached first, and a missing dump only surfaced as an error after `--output` was already gone. Both are now checked upfront. This also silently broke this very README's own documented workflow: `--avatar-overrides output/avatar_overrides.json` was destroyed by the `rmtree` before it was ever read back, on any normal (non-incremental) run — the overrides file is now loaded into memory before `--output` is touched.
- **Stored XSS via unvalidated URL schemes**: phpBB never validated a stored `[url=...]`'s scheme at write time, so a real dump can carry old spam/exploit content using one — confirmed: `[url=javascript:alert(1)]click[/url]` rendered as a live `<a href="javascript:alert(1)">` that executes on click. `_is_safe_url()` allowlists http(s)/ftp(s)/mailto plus scheme-less (relative/anchor) links; anything else becomes `href="#"` instead. Also HTML-escapes the `href` attribute value at all three link-rendering call sites, in case a URL ever contains a literal double-quote.
- **Path traversal via dump-provided filenames/URLs**: `copy_assets()` joined an attachment's `real_filename` directly onto its destination path; a `real_filename` containing `../../etc/x` resolved outside `assets/attachments/` entirely at copy time (confirmed: resolves outside the archive from six `../` segments). Now reduced to a bare basename first. Separately, `--url-mirrors`' local-file lookup joined a post's own `[img]` URL suffix directly onto the configured mirror directory; a `../../etc/passwd` suffix resolved outside it and would have read whatever's there instead (confirmed). Now requires the resolved path stay contained within the mirror directory before touching the filesystem.
- **Unapproved/hidden/needs-reapproval content rendered anyway**: `get_topics()`/`get_posts()` returned every row regardless of phpBB's own `topic_visibility`/`post_visibility` moderation state — the same protection phpBB itself applies before showing content to an anonymous/non-moderator visitor was simply absent. Confirmed: 53 posts and 9 topics at visibility=3 (`ITEM_REAPPROVE` — content a moderator pulled back for review, not currently meant to be public) in this dump. Both queries now require `visibility = 1` (`ITEM_APPROVED`); a topic that's still visible but has every one of its posts hidden falls through to the existing "missing post/topic content" fallback rather than rendering empty.
- **Cross-board link redirects**: `_rewrite_internal_link()` only checked whether a `viewtopic.php` link's `t=N` topic id existed in this archive — never the link's own host. A topic id is just a small integer, and confirmed on this real dump: 1,146 real links to `www.phpbb.com` and 457 to `rmcgirr83.org` alone (plus dozens of other real, unrelated phpBB boards), any of which could have a `t=N` that coincidentally also exists here, silently redirecting a reader to unrelated content instead of leaving the link pointing at the actual board they clicked through to. `_is_same_board_host()` now gates the rewrite on the link's own host: no host at all (relative/protocol-relative) is always same-site; anything else must match `board_hosts` — the dump's own `phpbb_config.server_name` plus any `--board-hosts FILE` extras, since a board's own domain can change over its lifetime (confirmed for real here too: phpbbmodders.net, .com, and .org are all really the same board at different points in its history). A community merged into this board from elsewhere is deliberately *not* added to that allowlist just because its links are common in the dump: its own historical topic ids aren't guaranteed to have been preserved 1:1 through the merge, and treating it as internal without that guarantee risks the exact same bug for a different reason.
- **Code-block content rewritten by other BBCode substitutions**: formatting/link/quote/list substitutions ran before `[code]` was ever converted, so they'd also fire *inside* a code block's own content — confirmed: `[code][b]literal[/b][/code]` rendered as real bold text instead of showing the BBCode example as it was actually written, silently changing an archived example into a different one. `_stash_code_blocks()`/`_restore_code_blocks()` extract `[code]...[/code]` into placeholders before anything else runs, then restore them last, HTML-escaped (a real code/HTML/PHP example can easily contain a literal `< > &`, which would otherwise be interpreted as actual markup rather than shown as the text it is) — except a literal `<br/>` landing inside one, which is phpBB's own line-break normalization rather than code content, and is restored as a real line break instead of escaped text. The same protection is wired into the XML-markup path too, which turned out to be where this actually mattered on this real archive: a post's overall content can be XML-wrapped (`<r>`/`<t>`) while still carrying old-style bracket-syntax `[code]` inside it, never converted to the XML `<CODE>` tag — confirmed on a real post, whose `[code]...[/code]` previously rendered as raw, unstyled bracket text sitting in the middle of a sentence with no code box at all.
- **Attachment ordering and duplicate rendering**: `get_attachments()` had no `ORDER BY`, but a stored `[attachment=N]` tag's numeric index was assigned by phpBB itself against its own retrieval order (`attach_id DESC` — confirmed against phpBB's own `viewtopic.php` query) when the post was originally written; returning a different order pairs a tag with the wrong attachment on any post with more than one. Confirmed on a real post with 18 attachments (rank/badge images), whose real `attach_id`s are in ascending insertion order in the dump — the opposite of phpBB's own descending retrieval order, so every `[attachment=N]` reference in that post was resolving to the wrong image. Fixed by adding `ORDER BY attach_id DESC`. Separately, `_append_trailing_attachments()`'s "already embedded inline" check ran against the pre-UID-strip text but only recognized a bare `[attachment=N]` tag — a real UID-tagged post (`[attachment=0:abcde]...[/attachment:abcde]`, the actual stored form for a legacy-BBCode post) never looked embedded and got appended a second time in the trailing section, duplicating it. Fixed by matching the optional `:uid` suffix too.
- **Stale feature output surviving `--incremental`**: an incremental run's cleanup only ever cleared `forums/`/`topics/`/`users/`/`index.html` — content gated behind a flag (`--search`'s `search.html`/`pagefind/`, `--sitemap-url`'s `sitemap.xml`/`robots.txt`, `--redirect-format`'s `.htaccess`/`nginx-redirects.conf`) wasn't in that list, since a normal run just regenerates it fresh. But a later incremental run that drops the flag, or switches `--redirect-format apache` to `nginx` (or back), left the earlier run's file sitting in `output/` indefinitely with stale or removed content. Reproduced for real: running `--redirect-format nginx` then `--redirect-format apache --incremental` left both `nginx-redirects.conf` (stale) and `.htaccess` in `output/` together. `clean_disabled_feature_output()` now removes each of these when the current run's flags no longer request it.
- **External-image discovery missed shapes the renderer already resolves**: `find_image_urls()` only recognized a bare `[img]url[/img]`/`<IMG src="...">` — a missing file just means the renderer finds nothing cached for that URL and silently drops the image, no error surfaced anywhere. Three real, confirmed gaps: (1) `[img:uid]url[/img:uid]` (the legacy-BBCode form, since the pattern required an exact `[/img]` close with no suffix) — 2 real occurrences; (2) a board that migrated from phpBB2 can carry a literal, unconverted `[img]<URL url="X">...</URL>[/img]` (see "Malformed `[img]` tags" above) that the renderer already resolves via its own case-(a) handling — **969 real posts**, by far the largest of the three, all silently losing their image; (3) `poll_title`/`poll_option_text` render through the same parser as post text and can equally contain `[img]`, but were never included in discovery at all (this dump's own 37 real polls happen not to use one, so this specific gap wasn't reproducible here, but the code-level gap was real and is fixed the same way). Total real discovery went from 462 to 1,239 URLs on this dump — 777 previously-silently-dropped images now found. Separately, a URL captured from XML attribute/text content has its `&` entity-escaped to `&amp;` per XML rules (confirmed real: 13 of the 969 migration-shape posts) — passed straight to an HTTP request, that breaks any query string with more than one parameter; `html.unescape()` is now applied at discovery time and at every `external_images` lookup on the render side, so the cache key stays consistent on both ends.
- **Forum descriptions and the board-wide announcement used the wrong relative path depending which page rendered them**: the same converted HTML was reused across `index.html` (site root, needs `assets/...`) and `forums/N.html` (one level down, needs `../assets/...`) — `render_forums()` was passed the site-root-depth parser instead of a page-depth-aware one, and `announcement_html` was converted once at the root depth and reused verbatim on `topics/N.html`/`forums/N.html` too. Confirmed real: forum 44 ("phpBB Project") has a description linking back to `viewtopic.php?f=44&t=...`, which the old code rewrote to `href="topics/12345.html"` — a link that 404s from `forums/44.html` (resolves to `forums/topics/12345.html` instead of the sibling `topics/12345.html`). A second parser instance, converting forum descriptions and the announcement once per depth actually used across the site, fixes both. See phpbb-archive security review, finding 12.
- **Double-escaped entities from raw XML content, introduced by two earlier fixes in this same list**: two real regressions, both from code that called `html.escape()` on text extracted directly from the raw XML document without first decoding it — XML already entity-escapes a real `&`/`<`/`>` in attribute values and text content, so escaping it again doubles it. (1) `<URL url="X">`'s href (the "Database-derived markup is treated as trusted HTML" fix above added `html.escape()` around it): a real `?a=1&amp;b=2` link rendered as `href="...?a=1&amp;amp;b=2"` — a browser reads that back as literal text `&amp;` glued onto the second parameter, not two real query-string parameters. Confirmed at real scale: **862 real topic pages** had this artifact before the fix. (2) `[code]` blocks inside XML-wrapped content (the "Code-block content rewritten by other BBCode substitutions" fix above): a real `<div>` typed as a code example, stored as `&lt;div&gt;` per XML rules, rendered as visible `&amp;lt;div&amp;gt;` text instead of the intended visible `<div>` — confirmed on **17 real topic pages**. Both fixed by `html.unescape()`-ing the raw XML-extracted text immediately, before any further processing — so the existing `html.escape()` calls re-escape it exactly once, correctly. Both counts confirmed at 0 on a full real regeneration after the fix.
- **Diagnostic modes (`-l`/`-m`/`-i`) shared the same asset-copying setup as a real run, unconditionally and without `--exclude`**: pointed at an `--output` a real deployment already used, any of the three would silently overwrite `assets/style.css` with the built-in default (discarding a real `--style-css` customization) and re-copy already-excluded private-message/excluded-forum attachments back into a real, possibly-published `output/` — the exclusion set is computed from `--exclude`, which none of the three diagnostic modes ever received. Fixed by giving `_open_db_and_copy_assets()` a `copy_assets_mode` ("full"/"avatars"/"none"): `-l`/`-i` need nothing written to `--output` at all now, and `-m` (which does need existing avatar files on disk to check resolution against) gets a new `copy_avatars()` split out of `copy_assets()`, touching only `assets/avatars/`. Separately, `-m`'s own starter-template output always wrote to whatever path `--avatar-overrides` pointed at — the exact path the README's own documented workflow tells a user to point it at — so re-running `-m` with overrides already supplied (checking what's still missing after filling some in) silently overwrote the hand-edited file with a fresh template covering only the still-missing subset. The generated template now always uses a name distinct from the supplied input path (`avatar_overrides.new.json` when one was given). Verified against phpbbmodders.net's own dump: `style.css`'s checksum and the attachment count were unchanged after a real `-l` run against the real deployed `output/`, and a real `-m --avatar-overrides output/avatar_overrides.json` run left that file byte-identical while writing its fresh template to `avatar_overrides.new.json`. See phpbb-archive security review, finding 14.
- **Polls and broader phpBB compatibility gaps (finding 15)**: four real, confirmed gaps fixed (two more sub-items from the original finding — numeric legacy avatar types, forum_id=0 global topics — don't reproduce on this dump at all: every avatar is a modern `avatar.driver.*` string, and there are zero forum_id=0 topics, so neither was touched here rather than guessed at). The poll-UID concern the finding raised turned out not to be a bug: `phpbb_topics`/`phpbb_poll_options` have no `bbcode_uid`-equivalent column at all, so `uid=""` was already correct.
  - **Moved-topic pointers rendered as ordinary topics with missing content**: a moved topic is a real "shadow" row phpBB leaves behind (`topic_moved_id` pointing at the real topic, now living in a different forum, sometimes a different `forum_id`) with zero real posts of its own — the old code just showed the generic "post content is missing" fallback. Now shown as `Moved: <destination title>` (matching phpBB's own real forum-listing convention) in both the forum listing (linking straight to the destination, same as phpBB does) and on the shadow topic's own page (for old bookmarks/search-engine links that still point at it). Confirmed real: 18 moved-topic rows, sample-verified end to end (topic 365 → 364, "TheFirstGeneration.com Website 21 Questions Feedback").
  - **Guest/deleted-account post authors lost their real name**: `poster_id=1` is phpBB's own reserved "Anonymous" account (confirmed real: `username='Anonymous'`, a real row) — every guest post rendered as a live link to that one generic account page, discarding the guest's real typed name (`phpbb_posts.post_username`) entirely. Confirmed real: 262 guest posts with real recorded names ("FrostByte", "RBCP", ...), plus 1 post from a genuinely deleted account. Both now fall back to `post_username` as plain text (no link, since there's no real profile) instead of linking to the shared Anonymous account or showing "Unknown" when a real name was actually recorded.
  - **`enable_sig` (per-post signature toggle) was ignored**: a post's signature visibility is a checkbox on that specific post, not a per-user setting — the same user's signature can legitimately show on some posts and not others. Confirmed real: 3,360 posts have it unset. Fixed in two places — the computed `sig_html` (already correctly gated) and, caught only by real-data verification after the first fix looked complete in isolated tests, `topic.html`'s own display condition, which was still checking `author.user_sig` (raw signature *text*, always present) instead of `author.sig_html` (the actual gated result) — so the fix silently did nothing until this was caught.
  - **`enable_smilies` (per-post smiley toggle) was ignored**: smiley codes rendered as images regardless of whether the poster disabled smiley conversion for that post. Confirmed real: 80 posts have it unset. `PhpbbBBCodeParser.convert()` takes a new `enable_smilies` parameter, threaded through both the legacy HTML-comment format and the XML `<E>code</E>` format — disabled leaves the original raw code text as-is (`<E>` case falls through to the existing "strip unknown XML tags" cleanup, matching how an unrecognized code already behaves).

## Private-forum exclusion

`--exclude` + `expand_exclusions_recursively()`: excluding a category excludes every descendant automatically — a forum can never end up orphaned (parent hidden, child still shown prominently at the top level), which is the wrong failure direction for a privacy feature. Excluded forums, their topics, and any attachment/external image used only inside them are never copied or downloaded, not just unlinked from the rendered HTML.

- **Password-protected forums (`phpbb_forums.forum_password`) weren't recognized as private content anywhere**: the column was tracked in every dump but nothing in `db.py`/`generate.py` read it, so the only way to keep one out of the archive was to notice it and add it to `--exclude` by hand. A password-protected forum is now auto-excluded by default (same treatment as `--exclude`, including recursive descendant exclusion and attachment/image exclusion) via a new `db.get_password_protected_forum_ids()`; `--password-override` (a JSON file of forum IDs, mirroring `--exclude`'s own shape) opts specific forums back in for an archive owner who knows the real password and consents to archiving that content. phpbbmodders.net's own real dump has zero forums with a password actually set, so this was verified by temporarily marking a real forum (125, "Modders MOD support") as password-protected in a throwaway copy of the dump: auto-exclusion correctly excluded it, `--password-override` naming it correctly included it, and a real regeneration of the unmodified dump confirmed zero behavior change (same 26 forum pages as before).

## Dark theme (`--theme dark`)

`generator/static/style-dark.css` mirrors the built-in `style.css`'s structure/selectors with a dark color palette, selected via `--theme dark` when no `--style-css` override is given — a custom `--style-css` is its own fixed palette and takes precedence either way.

## Favicon and board logo (`--favicon`/`--favicon-url`/`--logo`/`--logo-url`)

Neither a board's favicon nor its logo lives anywhere in a bare SQL dump. Both can come from a local file (`--favicon`/`--logo`) or be fetched live from a URL (`--favicon-url`/`--logo-url`, via `_download_image_asset()` — extension inferred from the URL path or the response's `Content-Type`); a URL that can't be reached (dead link, or blocked by something like a Cloudflare JS challenge a plain HTTP client can't pass) is skipped with a warning, the same graceful treatment as every other network fetch in this generator, rather than failing the whole run.

The logo's on-page size prefers phpBB's own configured `sitelogo_width`/`sitelogo_height` when set (real per-board metadata, not a guessed constant — e.g. a real board's own 324×308px file displayed at 84×80). Otherwise it's computed proportionally from the actual file's real dimensions via `_compute_logo_display_size()` — Pillow for raster formats, `_svg_natural_size()` (stdlib `xml.etree.ElementTree`, reading an SVG's own `width`/`height` or deriving from its `viewBox`) for vector ones — scaled to fit within a 50px height / 200px width box, never upscaling. A flat CSS `max-height` alone doesn't account for aspect ratio; a wide, short logo could still overflow width-wise with nothing but a height cap. `--logo-natural-size` shows the logo unscaled at its own original size instead of any of the above.

The header was restructured into a `.header-titlebar` (logo image beside a title/tagline block) so the logo and the site name/tagline stack sensibly regardless of whether a logo is present.

## Custom color scheme (`--style-css`)

The archive's own simple layout ships with a neutral default palette (`generator/static/style.css`). `--style-css FILE` swaps it for any stylesheet you point at. Every generated page `<link>`s `assets/style.css` rather than inlining it — the css is copied into `output/assets/` by `copy_assets()` on each run, and the same file can be dropped directly into an already-built archive's `assets/` to re-theme it without regenerating anything.

`docs/contrib/phpbbmodders-style.css.example` is a real-world example: colors approximating phpbbmodders.net's actual live `prosilver_se_revolution` child theme (dark charcoal page, brick-red frame and header/category bars) plus its base `prosilver` theme's link/text colors — pulled from the real CSS, not guessed, and verified against a full regeneration + browser render, not just visual inspection of the source.

The stylesheet link carries a `?v=<hash>` of `assets/style.css`'s own content (`env.globals["style_version"]`), so a re-themed or re-regenerated archive is picked up immediately instead of a browser serving a stale cached copy — `http.server` (and some real static hosts) sends only `Last-Modified`, no `Cache-Control`/`ETag`, so a browser can skip revalidation entirely. Doesn't affect the "drop a new `assets/style.css` into an already-built archive" workflow above: that leaves the HTML, and its query string, untouched either way.

## Board-wide announcement (`--announcement`)

`--announcement FILE` reads a plain-text BBCode file — written fresh for the archive itself (e.g. "this board is now a read-only archive"), not pulled from the dump — and renders it via the same BBCode parser used for post content (`uid=""`, since hand-written text has no phpBB UID annotation to strip). Shown on the index, every forum page, and every topic page. Omitting the flag, or leaving the file blank, renders nothing.

`docs/contrib/announcement.txt.example` is a worked example of the expected format.

## Sitemap and robots.txt (`--sitemap-url`)

Writes `output/sitemap.xml` (index, every forum, every topic, each with a `<lastmod>` from its most recent post) and `output/robots.txt` pointing at it. Requires an absolute base URL because sitemap entries must be absolute, unlike every other link the archive generates, which stays relative so the archive works at any path. Excluded forums/topics are already left out of `output/` entirely, so they're never in the sitemap either.

## Old-URL redirects (`--redirect-format`)

A static archive has an entirely different URL scheme than the live phpBB board it replaces (`topics/N.html` vs. `viewtopic.php?t=N`), and neither `sitemap.xml`/`robots.txt` nor Google Search Console's own removal tooling actually redirects a visitor (or a search engine) still using an old link — a proper 301 is the correct fix, and it's mechanical enough to generate rather than hand-write.

`--redirect-format {apache,nginx}` writes `output/.htaccess` (apache) or `output/nginx-redirects.conf` (nginx, `include`d into a `server {}` block) with one generic rule per old phpBB script (`viewtopic.php`, `viewforum.php`, `memberlist.php`), driven by whatever `t=`/`f=`/`u=` id is actually in the incoming request rather than an exhaustive per-page list — so the file stays small and never needs regenerating just because the archive's content changes, only if its own URL layout does. A `viewtopic.php` link's own `p=` post id is preserved as a `#pN` anchor on the redirect target. An id that isn't actually in this archive (excluded, or never existed) redirects to a page that 404s, the same outcome as no redirect rule at all.

The old board's scripts weren't necessarily reachable at the web root — phpBB tracks its own install path in `phpbb_config.script_path` (e.g. `/board` for a board installed at `.../board/viewtopic.php`), and the rules need to match that, not wherever this archive itself now lives. `--redirect-format` auto-detects it from the dump; `--redirect-old-prefix PATH` overrides it for a board that moved paths after the dump was taken (`--redirect-old-prefix ""` forces no prefix).

The redirect target itself is root-relative (`/topics/N.html`) by default, which only resolves correctly when the rule runs on the same host the archive is deployed to. When `--sitemap-url` is also given, the target becomes that absolute URL instead — needed when the redirect rule has to run somewhere other than the archive's own host, e.g. the old board's own subdomain (`board.example.com`) redirecting to a bare-domain archive (`example.com`).

Real-world example verified against phpbbmodders.net's own dump: `phpbb_config.script_path` is `/board` (a real non-root install), so the generated apache rule matches `board/viewtopic.php`, not just `viewtopic.php`. `phpbbmodders.net`'s own live board runs on Apache, so `run.sh` passes `--redirect-format apache`.

Caddy and Traefik are deferred — see [`docs/TODO.md`](TODO.md).

**Two real bugs found and fixed after syntax-only checking (`apachectl -t`/`nginx -t`) wasn't enough to catch them** — both surfaced only by actually running an isolated, localhost-only Apache/nginx instance and checking the real `Location` response header, not just config syntax:

- **Apache's `t=`/`p=` combined rule redirected to the wrong post entirely.** `%N` backreferences in `mod_rewrite` only ever come from the single *last* matched `RewriteCond` — confirmed against Apache's own docs — so having `t=` captured by one `RewriteCond` and `p=` by a second, separate one meant `%1` and `%2` both silently resolved to the second condition's own group. Reproduced live: `?t=42&p=99` redirected to `/topics/99.html#p` (the post id where the topic id belonged, and an empty anchor) instead of `/topics/42.html#p99`. Fixed by capturing both values in a single `RewriteCond`'s own regex. phpBB's real link order is `t=` before `p=` in the overwhelming majority of real links found in this dump, but not all — one real counter-example (`f=125&p=50434&t=10913`) was found, so a second rule handles the reversed order too, each internally consistent.
- **Apache also silently mangled the `#pN` anchor itself.** By default `mod_rewrite` percent-encodes `#` to `%23` in an external-redirect target (confirmed against Apache's own `[NE]` flag docs, and reproduced live without it) — turning `#p99` into `%23p99`, a dead anchor. `[NE]` is now set on both `t=`/`p=` rules (the only ones carrying a fragment).

nginx's `$arg_t`/`$arg_p` are independent named variables rather than condition-chain-scoped backreferences, so neither bug applies there — confirmed live against an isolated nginx instance too, `#pN` came through unescaped with no equivalent fix needed.

## Open Graph / Twitter Card meta tags

Every topic page carries `og:title`, `og:type`, `og:site_name`, `og:description` (the opening post's text, stripped of HTML and truncated via Jinja2's built-in `striptags`/`truncate` filters — no new Python code needed), and matching `twitter:*` tags, unconditionally — so a shared topic link shows a real title/preview instead of nothing. `og:description`/`twitter:description` are omitted gracefully when a topic's post content is missing from the dump. `og:url` is the one tag that needs an absolute URL; it reuses `--sitemap-url`'s value rather than introducing a second "what's my base URL" flag, and is simply omitted when that flag isn't set.

## Full-text search (`--search`)

Adds `search.html`, linked from every page's header (next to the "Static archive" tagline, styled like the site-title link) only when `--search` is actually used (`env.globals["search_enabled"]`, checked in `base.html` — the link isn't shown, and no dead link is generated, on a run without the flag), and indexes every generated page with Pagefind, a static client-side search engine, via the `pagefind[bin]` Python package — a real compiled search binary installed through pip, no Node.js needed. Runs as a subprocess after every other page is written.

The link originally lived in the breadcrumb bar, where it read as a fake breadcrumb level ("Board index · Search") rather than a utility link — moved to the header, out of the navigation trail entirely.

Result titles come from a `data-pagefind-meta="title:..."` attribute set on every page's `<body>` (via a new `body_attrs` template block in `base.html`) — without it, Pagefind defaults to each page's first `<h1>`, which on this archive is always just the site name, making every search result look identical. `search.html` itself is excluded from the index (`data-pagefind-ignore`) since it has no content of its own. The widget is re-themed via its own documented CSS custom properties (`--pagefind-ui-primary` etc.) rather than by fighting its markup — `docs/contrib/phpbbmodders-style.css.example`'s `#search` block is a real worked example.

Pagefind can't fetch its own index under `file://` — confirmed against Pagefind's own docs and by reproducing it: opening `search.html` directly as a file accepts a query and shows "Searching for…" but never returns results, with no error surfaced anywhere. Needs any real static file server (even a local one) to work at all.

## Broken-internal-link checker (`-c`/`--check-links`)

Unlike `-l`/`-m`/`-i`, which inspect the dump *before* generating, this inspects an already-generated `output/` *after* — it only makes sense to run once a real build exists. Walks every generated page's `href`/`src` attributes and flags a link to a file that doesn't exist, or a `#anchor` link whose target file exists but doesn't contain that anchor (e.g. `topics/106.html#p53377`, a permalink to one specific post that got excluded or was never recovered) — the anchor case is the more useful of the two, since it's not something you'd notice just by browsing. External URLs are out of scope; that's `--ignore-hosts`/`--url-mirrors`'s job. No new dependency — a regex over each file's text, not an HTML parser.

The regex is anchored to an actual opening tag (`<a ...href="..."` / `<img ...src="..."`), not a bare `href="..."` match anywhere in the file — found the hard way: a first pass against a real board's dump returned 6,351 "broken links," almost all of them phpBB template source code (`{U_FEED}`, `href="{T_THEME_PATH}/print.css"`, etc.) that someone had pasted inside a `[code]` block. Its `<`/`>` were correctly HTML-escaped so it couldn't be interpreted as a real tag, but the literal `"` characters in `href="..."` weren't, so a bare-substring regex matched it as if it were one. Anchoring to a real unescaped `<tagname` before the attribute fixed it — re-running against the same dump dropped the count to 19, and those remaining were pre-existing data quirks (a real `<a href="%27,%27">` from that same quoted source-array text, and a few spam posts missing a proper `http://` prefix), not archive bugs.

Two further false-positive sources, found on a subsequent pass against the same dump: the resolved path wasn't stripped of a trailing `?query` string before the filesystem lookup, so every page's own `style.css?v=<hash>` cache-buster was flagged as a broken link (12,439 false positives); and a percent-encoded href (an attachment with a space in its real filename, e.g. `Star%20Rates.zip`) wasn't decoded before comparing against the real on-disk names. Both are now handled before the lookup.

Real-world starting points for `--ignore-hosts`, `--style-css`, `--announcement`, and `--board-hosts`, with its own README explaining what pairs with what. Config-shaped files follow a `<name>.<ext>.example` naming convention; scripts don't, since they're run directly rather than edited into a live config. `known-dead-hosts.json.example` seeds a fixed live filename (`known-dead-hosts.json`, gitignored, conventionally kept at the repo root — see `.gitignore`); `phpbbmodders-style.css.example`, `announcement.txt.example`, and `board_hosts.json.example` don't — `--style-css`/`--announcement`/`--board-hosts` take an arbitrary path, so a live copy can go anywhere, or the example can be pointed at directly. `known-dead-hosts.json.example`'s hostnames (parked domains, shut-down image hosts, or previously misclassified ones corrected after direct verification) were confirmed dead against a real dump, not a generic guess. `board_hosts.json.example` lists this real board's own three historical domains (`.net`/`.com`/`.org`), each confirmed by real links found in the dump. `run.sh` pairs with no single flag — it's phpbbmodders.net's real wrapper script, showing how every flag composes into one command. `serve.sh` serves a generated `output/` over real HTTP with Python's built-in server, needed to actually test `--search` locally since Pagefind can't fetch its own index under a `file://` path.

## Operational fixes

- **Self-healing `.venv`**: `generate.sh` detects a broken virtualenv (its console-script wrappers hardcode an absolute shebang path back to the venv at creation time, so copying/moving the containing folder silently breaks `pip` etc. even though the `python` binary keeps working) and recreates it instead of failing.
- **`generate.sh` convenience wrapper**: sets up `.venv` if missing, installs dependencies, runs the generator — one command instead of three.
- **`--regen-light`**: `--incremental` already skips re-fetching anything that succeeded before, but still retries every URL that failed last time (in case a temporarily-down host recovers) — on a real dump with hundreds of permanently-dead hosts, that retry cost (a fixed network timeout per URL) dominates a run even when the only actual change is a template/logic edit with nothing to do with images at all. `--regen-light` (implies `--incremental`) skips the network entirely for anything not already cached in an existing `output/`, instead of attempting and retrying — for quickly re-rendering HTML against an `output/` a full run has already populated. Confirmed real on phpbbmodders.net's own dump: a full `--incremental` run took ~30 minutes (dominated by retrying hundreds of dead-host timeouts); the same dump with `--regen-light` against that same populated `output/` took 4m50s (`time`-measured) with zero network attempts (`grep`-confirmed: no "Image URL unreachable"/"host is on the ignore list" lines at all) — about 6x faster, reusing exactly what was already cached (278/989 external images, 5/14 avatars). The remaining time is the MySQL dump import and template rendering itself (4,296 topics / 8,115 users / pagefind indexing 12,438 pages), not network I/O.
- **`known-dead-hosts.json.example`**: extended with 24 additional real hostnames confirmed dead by DNS resolution failure (`Name or service not known`) across this session's regeneration logs — ambiguous cases (an HTTP 403 from an actively-live major site like sourceforge.net, or a generic timeout that could be a slow-but-live host) were deliberately left out, since `--ignore-hosts` skips a listed host unconditionally and forever; only a definitively-gone domain belongs there.
